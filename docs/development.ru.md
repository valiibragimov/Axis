# Разработка

Все npm-команды ниже выполняются из корня репозитория, если не указано иное. Используйте Node 22.12+ в ветке Node 22 (`.nvmrc`) и устанавливайте зависимости каждого пакета по lock-файлу:

```sh
npm ci
npm ci --prefix server
npm ci --prefix functions
```

## Основное приложение с локальными эмуляторами

Требуется Java 21+. Запустите `npm run dev:local` и откройте <http://127.0.0.1:5050/login.html>. Зарегистрируйте локальный аккаунт и создайте проект. Используются обычная сборка приложения, настоящий Firebase SDK, правила Firestore и Express API; заменяющих адаптеров нет.

Эмуляторы доступны только на loopback: Firestore `28085`, Authentication `29099`, Storage `29199`. Порты задаются в `firebase.emulator.json`. Зарезервированный Firebase-префикс проекта `demo-` обозначает изолированные тесты, а не отдельный интерфейс. Локальный запуск не загружает сохранённые экспорты и не меняет `.env`. Данные эмуляторов временные.

## Приложение с Firebase

Скопируйте [.env.example](../.env.example) в `.env` и заполните все шесть значений веб-конфигурации из отдельного Firebase-проекта для разработки. Они включаются в клиент при сборке. Учётные данные Admin в этот файл добавлять нельзя.

Включите провайдеров входа для тестовых аккаунтов и разрешите локальное имя хоста в Firebase Authentication. Создайте Firestore и настройте [правила](../firestore.rules) и [индексы](../firestore.indexes.json) из репозитория в тестовом проекте. Не заменяйте настройку правилами, разрешающими доступ всем.

```sh
npm run build:client
python -m http.server 8000 --bind 127.0.0.1
```

Откройте <http://127.0.0.1:8000/> и войдите тестовым аккаунтом. В этом режиме данные сохраняются в настроенный Firebase-проект. Используйте синтетические проекты и модели.

Отдельного клиентского dev-сервера и команды hot reload нет. После изменений запускайте `npm run build:client`. `build/pages/index.html` собирается из [HTML-фрагментов](../src/client/index-partials); редактируйте их, а не сгенерированную страницу.

## Необязательный Express API

Рабочая область умеет разбирать IFC и готовить текст отчёта в браузере. Запускайте API для разработки серверных сценариев.

Скопируйте [server/.env.example](../server/.env.example) в `server/.env`. Настройте доступ Firebase Admin к тому же тестовому проекту через параметры сервисного аккаунта из шаблона или Application Default Credentials. Оставьте `AUTH_REQUIRED=true`: API проверяет Firebase ID tokens и права доступа к проекту.

```sh
npm run dev --prefix server
```

Команда компилирует сервер, следит за изменениями TypeScript и перезапускает Node. Порт по умолчанию — 5050. Для запуска готовой сборки без отслеживания изменений:

```sh
npm run build:server:ts
npm start --prefix server
```

Адрес API отчётов задаётся во время выполнения и не подставляется из корневого `.env`. До загрузки модулей приложения страница должна определить `window.__APP_CONFIG__` с полем `AI_REPORT_API_BASE`. Укажите origin локального API для серверных отчётов или оставьте поле пустым для подготовки текста в браузере. Добавьте точный origin статического клиента в серверный `ALLOWED_ORIGINS`.

Сейчас рабочая область импортирует IFC через браузерный Worker и публикует данные напрямую через адаптер Firestore. Серверная точка IFC — отдельный API-сценарий; существующее поле конфигурации `BIM_IMPORT_API_BASE` не переключает на него рабочую область.

Лимиты workers и запросов описаны в `server/.env.example`. Дополнительный параметр `IFC_WORKER_MAX_BYTES` ограничивает размер входных данных worker в байтах, по умолчанию 25 MiB. Согласуйте его с HTTP-лимитом тела запроса. Ограничения кучи V8 не ограничивают память WASM.

Firebase Function в [functions/src/index.ts](../functions/src/index.ts) обслуживает новостную ленту профиля. Она отделена от API проверок и не запускается командой локальных эмуляторов.

Chart.js и jsPDF загружаются по необходимости из локальной сборки; рядом сохраняются их лицензии. Внешний CDN скриптов не требуется.

## Результаты сборки

`npm run build` очищает генерируемые файлы приложения, компилирует клиент, сервер и Functions, собирает ленту профиля, затем формирует и проверяет `dist-hosting`. Команда ничего не развёртывает.

| Каталог | Назначение |
| --- | --- |
| `dist/` | Браузерные модули, workers и ресурсы просмотрщика |
| `build/pages/` | Сгенерированные HTML-страницы |
| `dist-hosting/` | Статические файлы для хостинга |
| `server/dist/` | Скомпилированный Express API и общий серверный код |
| `functions/dist/` | Скомпилированная Firebase Function |

Service worker компилируется в `dist/sw.js`. Исходники находятся в `src/client/pages`, `src/client/index-partials`, `src/client/styles` и `src/client/assets`, профили компилятора — в `config/typescript`. Публичные URL сохранены.

## Восстановление записи проверок

Исходная проверка и её представление в `inspections` записываются атомарно. Существующие ID реестра сохраняются, новые включают исходную коллекцию. Сессии журнала получают номер проверки в той же транзакции. Повтор создания с тем же ID проверки или сессии означает ту же операцию.

Дополнительное поле проекта `inspectionSync` содержит версию `1`, токен ревизии и признак `pending`. Пересчёт аналитики снимает этот признак только при совпадении ревизии. При отказе маркер остаётся в Firestore; повторное открытие модулей проверок запускает восстановление. Сводка не использует ожидающий пересчёта агрегат как резервный источник. Миграция исходных записей и backfill не требуются: проекты без поля остаются читаемыми. При откате прежний клиент читает исходные проверки и реестр, игнорируя маркер; для завершения отложенного пересчёта нужно открыть проект обновлённым клиентом. При откате сохраняйте маркеры незавершённого пересчёта.

## Проверки

Сохранение проверки ищет старые связи реестра индексированными запросами по ID источника и документа вместо полного чтения проекта. Массовое удаление один раз группирует связи выбранного модуля. Одновременные запросы восстановления аналитики объединяются по проекту; новое сохранение запрашивает заключительную проверку ревизии, а сбой сохраняет устойчивый маркер восстановления. Карточки сводки, план контроля и подробная аналитика используют успешные чтения коллекций текущего запроса с указанием ID проекта. Для неудачных чтений сохраняется прежний резервный путь; постоянный кэш чтений и миграция данных не добавляются.

Перед отправкой изменений приложения выполните команды из [README](../README.ru.md#разработка-и-тесты).

- `npm test` пересобирает приложение, затем запускает smoke-тесты, тесты основных модулей и браузерные сценарии.
- Если синтетические проверки используют `FIREBASE_CONFIG_MODE=test` рядом с заполненным локальным `.env`, `npm test` восстанавливает локальную конфигурацию входа и обновляет кэш service worker после успеха или ошибки. CI без локального `.env` сохраняет тестовую конфигурацию. После проверок обновите `login.html`.
- `npm run test:core` собирает сервер и запускает тесты прикладного слоя, workers и IFC.
- `npm run test:ui` собирает основное приложение и запускает браузерные тесты с Authentication, Firestore и Storage Emulator. Тестовые записи изолированы; для доступа к эмуляторам нужна Java 21+.
- `npm run test:integration` собирает сервер и запускает Firestore Emulator на loopback-адресе с [firebase.emulator.json](../firebase.emulator.json). Нужна Java 21+. Используется проект `demo-`, а не реальные учётные данные.
- `npm run audit:all` проверяет lock-файлы всех трёх пакетов.

В Linux установите Chromium и его системные зависимости командой `npx playwright install --with-deps chromium`. В Windows тесты запускают установленный Google Chrome.

[CI](../.github/workflows/ci.yml) использует тестовые значения веб-конфигурации Firebase для сборок. Тесты работают с синтетическими данными и не должны зависеть от данных реальных проектов.
